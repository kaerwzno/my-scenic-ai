## D4：情绪识别 = 先只做"语音"这条

| 项 | 内容 |
|---|---|
| **时间** | 2026-09-25 |
| **决策** | 情绪识别**目前只做语音这一路**（不做摄像头/表情识别） |
| **理由** | 语音是陪伴场景最自然的输入；摄像头涉及隐私与伦理，延后 |

### 三段式实施路径（从最省事开始）

| 阶段 | 做法 | 增量成本 | 建议 |
|---|---|---|---|
| **1** | ASR 转文字 → **文字情绪判断** | **几乎为零**——ASR 本来就要做；Fay 已内置关键词情绪分析 | ★ **先做这个** |
| 2 | 加声学特征（音量 / 语速 / 停顿） | 中——需从音频抽特征 | 陪伴场景**必要** |
| 3 | 专门的语音情感识别模型（如 Emotion2Vec） | 高——要装模型 / 微调 | 看效果再定 |

### Fay 里已有的情绪通路（可直接用）

| 能力 | 位置 | 说明 |
|---|---|---|
| 关键词情绪分析 | `core/fay_core.py:3076` `__analyze_sentiment_by_keywords` | 返回 **-2 ~ +2**，四档关键词表（非常积极/积极/消极/非常消极） |
| 百度情感 API | `ai_module/baidu_emotion.py` | 需配置 `baidu_emotion_app_id` 等 |
| 情绪提示字段 | `config/action_rules.csv` 的 `sentimentHint` | 规则表里已带情感倾向标注 |

### ⚠️ 一个必须记住的技术限制

**文字情绪 ≠ 真实情绪。**

孩子说"我没事"，但语气是哭腔——**纯文字判断会判错**。

所以阶段 1 只能算"能用"，**陪伴场景真正需要的是阶段 2**（声学特征）。
这一点在景区场景可以容忍，在陪伴场景不能。设计时不要忘记。

## D5：★ "主动"的送达方式受微信平台限制（必须提前知道）

| 项 | 内容 |
|---|---|
| **时间** | 2026-09-25 |
| **问题** | 小程序是"用户主动打开"的，那数字人怎么"主动"？ |

### 两种"主动"，可行性完全不同

| 类型 | 场景 | 技术手段 | 可行性 |
|---|---|---|---|
| **在场主动** | 用户已打开小程序、正在游览，数字人主动开口 | 小程序内 SSE / WebSocket 推送 | ✅ **完全可行**，不需要任何微信特殊能力 |
| **离场主动** | 用户没打开小程序，也要收到数字人的话 | **微信订阅消息（服务通知）** | ⚠️ **受平台限制** |

### 微信订阅消息的限制（需实际确认，以官方最新规则为准）

- **一次性订阅**：用户授权一次，只能推**一条**
- **长期订阅**：仅限特定行业（政务、医疗、交通等），**旅游 / 景区大概率不符合**

**推论**："我下周还来，到时候提醒你"这种**跨天的主动提醒**，受此限制难以直接实现。

### 应对方案（建议 A + C 组合）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 主动限定在"在场"** | 用户下次打开小程序时，数字人主动提起："您上周说过这周末要来，今天正好是周末" | ★ **推荐**——不需要微信推送能力 |
| B. 争取一次性订阅 | 关键节点推一条 | 可作为补充 |
| **C. 补一句"攒下的问候"** | 用户下次打开时，把这段离线期间攒下的主动内容补上 | ★ **推荐**——体验上"它一直记着你" |

### 关键判断

> **景区导览的主动，绝大部分场景本来就是"在场"**（用户正在游览时提醒），
> 所以这个限制**影响不大**。真正受影响的是"离开景区之后的关怀"。
> 而陪伴场景恰恰需要"离场关怀"——**这一点到那时要重新设计**。

## D6：★ 知识保护机制（受保护知识）

| 项 | 内容 |
|---|---|
| **时间** | 2026-09-25 |
| **决策** | 给知识块加**保护标记**，让自动优化碰不到它 |
| **时序要求** | ⚠️ **必须在自进化跑起来之前装好** |

### 为什么需要

自进化的降级规则是「没人问的知识 → 降低层级」，它看的是**使用频次**。

> **消防栓一年用不上一次，但不能因为"没人用"就把它拆了。**
>
> 自进化 Agent 会看到消防栓的使用频次是 0，然后一本正经地建议降级。
> 它按规则办事，规则本身没错——**错的是规则没区分"冷门"和"不该冷门"**。

### 它管三件事

| # | 管什么 | 为什么 |
|---|---|---|
| 1 | 不能被**自动降级** | 使用频次低 ≠ 不重要 |
| 2 | 不能被**自动删除** | 同上，更严重 |
| 3 | 不能被**自动改写** | ★ 最易忽略——把"紧急疏散路线"改写错方向，比不答更糟 |

**受保护知识只允许人工修改，Agent 最多只能"建议"。**

### 数据字段（与已有字段的职责划分）

```json
{
  "priority": 100,             // 已有：权威性/时效性（人工维护，用于事实覆盖）
  "usage_score": 0.0,          // 新增：使用频次（自进化自动调整）
  "protected": true,           // 新增：受保护
  "protect_reason": "safety"   // 新增：保护原因（便于审计）
}
```

| 字段 | 谁改 | 作用 |
|---|---|---|
| `priority` | 人工 | 事实冲突时选赢家（新票价覆盖旧票价） |
| `usage_score` | 自进化 | 检索排序的热度加权 |
| `protected` | 人工（自动初判辅助） | 自进化碰不到它 |

> ⚠️ **不要把"用户关注度"塞进 `priority`**——那会污染它的语义，
> 导致"大家都爱问的旧票价"压过"没人问的新票价"。所以热度用独立字段。

### 怎么判定

**自动初判 + 人工可改**：

| 方式 | 做法 |
|---|---|
| 自动初判 | 按关键词：安全 / 禁止 / 注意 / 危险 / 紧急 / 疏散 / 医疗 / 救护 / 无障碍 / 轮椅 / 失物 / 投诉 |
| 按来源 | 官方资料默认保护，用户上传的默认不保护 |
| 人工可改 | 管理端能看到标记，可手动加/取消 |

### 配套机制：来源白名单（防污染）

受保护防的是"**别弄坏已有的**"，白名单防的是"**别学错**"。

**规则**：自进化生成的候选知识**只能来自可信来源**（官方资料、管理员上传的原文），
**绝不能从"用户说的话"生成**。

> 反例：很多游客问"门票是 100 元吗？"（错误前提），Agent 若采信了"100 元"，
> 就会把错误信息写进知识库。这是真实存在的污染路径。

**一个防降级，一个防污染，两者是一对。**

### 在陪伴场景会更关键

| 受保护知识 | 为什么 |
|---|---|
| 危机干预（自伤、走失、情绪崩溃） | 极端低频，极端重要 |
| 过敏 / 用药信息 | 出错代价极高 |
| **家长设定的硬约束**（"不要提某某话题"） | 这不是知识，是**红线** |
| 情绪安抚的边界 | 说错话会伤到孩子 |

那时"受保护"可能不只是"不降级"，还应该是"**强制注入上下文**"。

### 转换策略

```

        ↓  每个景点 × 每个有内容的字段 = 一条知识块
```

### ★ 资料包缺两栏（要补）

旧项目的知识块是 7 栏，**含"信息类型"和"可回答问题"**；
而这份资料包有 11 栏，**没有这两栏**——恰恰是结构化快答的关键：

| 缺失字段 | 作用 | 怎么补 |
|---|---|---|
| `info_type` | 意图匹配（"多高" → 参数类） | ✅ 已由字段名映射自动补上 |
| `questions` | 别名命中（用户会怎么问） | ⬜ **要用 LLM 批量生成** |
| `tags` | 同义说法匹配 | ⬜ **要用 LLM 批量生成** |

### 保护标记判定的两条教训（实测踩出来的）

**教训 1：只看关键词会误判，要看语境。**

```
反例：「路面采用【防滑】材料铺设」   ← 产品描述，不该保护
正例：「雨天湿滑，【需注意】安全」   ← 安全提示，该保护
```

改进：safety / conduct 要求「**关键词 + 提示性动词**（需注意/小心/请勿）共现」。

**教训 2：分类不够用。** 原本只有 safety / service 两类，实测发现还需要 **conduct**（行为规范 / 文物保护）。

现在分三类，**优先级 safety > service > conduct**：

| 类型 | 例子 |
|---|---|
| `safety` | 雨天湿滑、禁止游泳、注意防滑 |
| `service` | 行动不便可乘观光车、医疗点、失物招领 |
| `conduct` | 禁止喧哗、禁止触摸文物、禁止闪光灯 |

**判定原则：宁可多标，不可漏标。**
误标 → 白保护一条（无害，可人工改回）；漏标 → 安全知识可能被降级（有害，且事后查不出是哪几条）。

### 转换过程中踩的三个坑（都值得记）

| # | 坑 | 根因 | 后果 |
|---|---|---|---|
| 1 | **info_type 撞车**（踩了两次） | ① "具体位置"和"核心功能"都映射成"位置与功能"<br>② 5 条专题知识的 `spot_name` 为空，subject 全退化成"灵山胜境" | **事实冲突门控（key = 景点+信息类型）会把它们互相覆盖，丢数据** |

## D8：游客端改为网页，不强行走小程序（2026-09-25）

**这一条推翻 D1 的一半**（D1 说"最终展示界面 = 微信小程序"）。D1 里关于"主动送达受微信限制"（D5）的分析仍然有效，
但那个限制现在只影响"小程序端"这一条可选路径，不再是必须解决的约束。

### 决定

游客交互界面**改成网页**，小程序**保留但不再投入**（降级为"以后想加就加的第二端"）。

### 为什么

不是"图省事"，是**网页在技术上全面占优**，而且我们这几天在小程序上卡的每个点，网页上都不存在：

| 卡住的地方（小程序）| 网页上 |
|---|---|
| 拿不到音频数据，口型只能预计算包络 | **Web Audio API 可实时分析音频** |
| Live2D 没有现成方案（GitHub 零案例） | **官方 Cubism SDK 直接支持** |
| Cubism 依赖 DOM，搬进小程序要自己造适配层 | 原生可用 |
| 不支持 WebRTC，实时流走不通 | 支持 |
| 调试要靠猜（模型没有浏览器） | **F12 一眼看到** |

另外两条现实理由：

1. **小程序的账号 / 审核 / 备案是纯额外负担**，对论文和演示没有增益。
2. **网页更贴合终极场景**——孤独症陪伴是家长在平板/电脑上用，不需要微信生态；
   答辩演示也用笔记本更顺。

### 不影响的部分（这是重点）

已经做的工作**分层是清楚的，只换最上面那层**：

```
游客界面（网页 或 小程序）   ← 只有这一层换
        ↓
BFF（miniprogram-api）       ← 不动：7 个接口都是 HTTP
        ↓
Fay + 知识库 + 记忆           ← 不动
```

可以直接复用：

- **BFF 的接口**（用户档案、形象选择、聊天收发、音频代理）
- **WS 订阅器**（口型 + 表情）—— 网页一样用
- **形象池** `avatars.json` + 5 个形象 + 灵灵的 7 张表情差分
- 预启动机制、知识库自进化那一整套

**这反过来验证了「驱动可插拔」这个架构设计是有用的**：换终端不用动后端。

### 明确的否定项

**不要把 Fay 自带的那个前端当游客界面。** 实测它是个**控制面板**：
页面里有「预启动工具」「MCP 在线状态」「添加用户」「用户画像编辑」——
那些是给管理员看的，暴露给游客不合适；而且它的"数字人"就是三张静态图换来换去。

→ 新建一个轻量的游客网页，复用后端，界面按游客的需要做。
