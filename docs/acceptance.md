### ★ 第 2 步：用第二个插件证明"可插拔" ✅

**做法**：把示范资料包按景区**拆成两个独立知识库**，代码原样复制。

| | `plugins/kb-lingshan` | `plugins/kb-nianhuawan` |
|---|---|---|
| **`server.py` 代码** | ★ **两者 MD5 完全一致** | 同 |
| `plugin.json` 清单 | slug=`lingshan`，名=灵山胜境 | slug=`nianhuawan`，名=拈花湾禅意小镇 |
| 语料 | 128 条（16 个灵山景点 + 5 专题 + 票价） | 42 条（6 个拈花湾景点） |
| 受保护知识 | 8 条 | 7 条 |
| 暴露的工具 | `lingshan_query` / `lingshan_stats` | `nianhuawan_query` / `nianhuawan_stats` |

**新增一个知识库 = 复制代码目录 + 写一份 `plugin.json` + 放语料 + 建索引。代码一行不改。**

**路由验证（决定性）**：

```
问「灵山大照壁有多长多高？」      → Fay 调用 [lingshan_query]    → 答：长39.8米，高7米
问「拈花湾五灯湖晚上有什么表演？」 → Fay 调用 [nianhuawan_query]  → 答：《禅行》灯光秀 19:00/20:00 各一场
```

**Fay 能按问题所属景区，正确路由到对应的知识库插件。**

#### 附带发现：Fay 会自我纠正参数错误

第一次调用 `nianhuawan_query` 时 Fay 传了 `{"question": "..."}`，工具报
`query Field required`；**Fay 自己改成 `{"query": "..."}` 重试并成功**。
这是 agent 相对固定流水线的能力之一。

#### 过程中解决的三个问题

| # | 问题 | 解法 |
|---|---|---|
| 1 | **工具名会撞车**：两个插件都叫 `query_knowledge`，而 Fay 的工具注册表**按工具名聚合**（`faymcp/tool_registry.py` 的 `_rebuild_cache_locked`），同名会互相覆盖 | 工具名**从 `plugin.json` 的 slug 派生**（`lingshan_query` / `nianhuawan_query`），代码仍完全一致 |
| 2 | **重建索引时报 `PermissionError`**：索引文件被正在运行的 MCP server 占用 | 重建前先 `POST /api/mcp/servers/{id}/disconnect`，重建后 reconnect |
| 3 | 插件描述写死成"灵山胜境 / 拈花湾" | 描述也放进 `plugin.json`，代码只读不写 |

### ★ 第 3 步：`ingest_document` —— 知识库能"写"了 ✅

**新增文件**：`ingest.py`（与 `server.py` 一样，两个插件各有一份、**代码完全一致**）

#### 三个设计要点

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **上传内容同时落 `corpus/uploaded.json`** | 只写 Chroma 的话，重建索引会把上传内容冲掉。`build_index.py` 现在读 `knowledge.json` + `uploaded.json` **两份** |
| 2 | **复用同一套保护判定** | 上传的内容也自动打保护标记（含"需注意 + 湿滑"等会被标记） |
| 3 | **内容 hash 去重** | 同样的内容重复上传不会写两遍 |

#### 实测（2026-09-25）

**入库**：

```
上传一段测试文档（夜游开放时间 + 安全提示）
  → 切块 2 条（按 Markdown 标题）
  → 入库成功，库内 128 → 130
  → "安全提示"那条被自动标为受保护 🔒
  → uploaded.json 落盘 2 条
```

**重建索引不丢数据**：重建后仍是 **130 条**，且再查"夜游什么时候开放"仍能命中（距离 0.3837）。

**端到端（经 Fay）**：

```
问：灵山有夜游吗？几点开始？
Fay → [lingshan_query]
      参数被 Fay 自己扩展为：「灵山有夜游吗？夜游几点开始？夜间开放时间、夜游场次和游玩须知」
      命中 2 条刚上传的内容（相关度 0.7503 / 0.704）
答：有的～灵山胜境自2026年起新增夜游，开放时间是18:30-20:30，从九龙灌浴广场进入。
    夜游期间台阶照明会比较暗，雨天路面也容易湿滑，走路记得放慢一点、注意脚下哦。
```

**答案同时用上了两条上传内容**（开放时间 + 安全提示），且安全提示那条因受保护而带「重要提示」标记。

#### 附带发现：Fay 会自己做查询扩展

它把「灵山有夜游吗？几点开始？」自动扩写成
「…夜间开放时间、夜游场次和游玩须知」——**这是 agent 的主动行为**，
我们的插件只需要把 query 原样拿去检索即可。

## 验收点 3：数字人能主动开口 ★核心

| 项 | 内容 |
|---|---|
| **验收时间** | 2026-09-25 |
| **结论** | ✅ **通过**（机制 + 事件源均已实现；C/D 的"优先级修复"仅以 dry-run 验证） |

### 怎么验

向 Fay 的主动接口推一个"事件"，看它会不会**结合已有记忆**生成个性化话语。

```powershell
$json = @{
  username    = "User"
  observation = "用户刚到达灵山大佛，正站在登云道入口，前方需要攀爬216级台阶"
} | ConvertTo-Json
$bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
$r = Invoke-RestMethod -Uri "http://127.0.0.1:5000/to-greet" `
  -Method Post -ContentType "application/json; charset=utf-8" -Body $bytes
```

### 实测结果（✅ 关键机制通过）

事件推入后，Fay 的主动回应**同时体现了人格与记忆**：

- 它知道自己的名字是「**灵灵**」（人格设定生效，`config.json` 的改名已起作用）
- 它**记得用户腿脚不好**（此前通过对话存入的记忆，被主动回应的生成过程检索到了）

**结论**：`/to-greet` → `observation` 入记忆 → 结合已有记忆 → 生成个性化主动话语，
**整条链路成立**。这不是固定话术，是真正的"带着记忆的主动关怀"。

### 为什么这一条重要

它同时验证了 README 里"主动"与"记忆"两项核心能力的**联动**：

> 如果只验证记忆，得到的结论是"它记得住"；
> 但**"记得住 + 主动用得上"** 才是"陪伴"与"问答机器人"的真正分野。

### 事件源实现：`scripts/proactive_watchdog.py`

**做成了真的，不是预制**：持续观察 Fay 里**真实**的对话数据（真实时间戳、真实消息长度），
条件满足才推 observation。唯一人工设定的是阈值（多少分钟算久）——那是产品参数，不是内容。

三条规则（用户选定）：

| 规则 | 触发条件 | 实测 |
|---|---|---|
| **B** 逛久了 | 已游览 > N 分钟 | ✅ **真实触发成功** |
| **C** 快闭园 | 距闭园 < N 分钟 | 🟡 修复后 dry-run 验证通过，真实触发未测 |
| **D** 回复很短 | 最近 N 次回复都很短 | 🟡 同上 |

防打扰三层：**全局冷却**（主动后 300 秒不说话）/ **单规则冷却** / **安静期**（用户刚说话时 B/C 不打扰）。

### ★ 实测中发现并修复的两个 bug（值得记）

**bug 1：多条规则同时命中时，只发第一条（按代码顺序），没有优先级**

实测现象：C 和 D 的条件明明都满足了（`距闭园=19.1分钟`、`最近两条长度=[1,1]`），
但触发的始终是 B——因为 B 在代码里排在前面，被 `triggered[0]` 永远选中。

**修复**：给规则加 `priority` 字段，按优先级排序后取最高。
默认 **C(100) > D(60) > B(20)**——快闭园最紧急，用户状态次之，"逛久了"最不紧急。
同时输出"被压住的规则"，让判断过程可见。

> 这个 bug 很典型：**三条规则单独测都能过，一起测就互相屏蔽**。
> 如果只测一条规则，会误判为"功能正常"。

**bug 2：`/to-greet` 的 HTTP 返回里 `data` 常常是空的**

原因：该路径下生成的文本走 **WebSocket 推给面板**，同时落库，但不回填 HTTP 响应体。

**修复**：改成推送后**从消息库读回**最后一条数字人消息（`wait_for_reply`）。

> 教训：**不要假设 HTTP 响应体里有你想要的东西**，要去看真实数据落在哪。

### 附带确认：observation 会长期留在记忆里

`record_observation` 会为观测生成一条 **`observation` 类型**的长期记忆节点。

**双面影响**：

- 正面：数字人真的"记得住经历"，将来能提起"您上次到达灵山大佛时…"
- 风险：**测试数据会污染真实记忆**，正式使用时要区分测试与真实观测

## ⚠️ 过程中发现的问题（必须记档）

### 问题 1：记忆落盘时机对陪伴场景不安全

**现象**：聊了几句话之后，`nodes.json` 仍是空的 `[]`（还是 2026-09-21 的原始占位文件）。

**根因**（已定位到代码）：

`save_agent_memory`（把记忆从内存写入磁盘）**全仓库只有三个调用点**：

| 位置 | 触发时机 |
|---|---|
| `fay_booter.py:356` | **Fay 优雅退出时** |
| `nlp_cognitive_stream.py:1167` | **每天 0 点**（`schedule.every().day.at("00:00")`） |
| `genagents_flask.py:173` | 只在"克隆人格"功能里 |

**没有 HTTP 接口可以手动触发保存。**

**影响**：

进程崩溃 / 断电 / 被强杀 → **当天所有记忆丢失**。
对"长期陪伴"定位是**致命风险**——用户以为它记得，其实没记住。

**结论**：正式做陪伴场景前必须解决。可选方向：

- 改成定时落盘（如每 N 分钟）
- 或每次对话结束后异步落盘
- 或提供手动保存接口

**状态**：⬜ 待修

### 问题 2：缺少细粒度记忆管理

当前只有两个粗粒度接口：

| 接口 | 粒度 |
|---|---|
| `/api/delete-user` | 删掉某用户的整个记忆目录 |
| `/api/clear-memory` | 清空**所有**用户记忆 |

**缺**：查看单条记忆、纠正单条记忆。

**影响**：违反 README 里的红线 3（记忆必须可查看、可纠正、可删除）。陪伴场景里"记错了"比"不记"更糟。

**状态**：⬜ 待开发

### 问题 3：Fay 装的 mcp 是 2.x，与它自带的范例写法不兼容

**现象**：照抄 Fay 官方范例 `mcp_servers/yueshen_rag/server.py` 的写法，连接时报：

```
AttributeError: 'Server' object has no attribute 'list_tools'
```

**根因**：Fay 的 `requirements.txt` 里 `mcp` 未锁版本，实际装的是 **mcp 2.x**。
该版本里：

| 版本 | 高层 API |
|---|---|
| mcp 1.x | `from mcp.server.fastmcp import FastMCP` |
| **mcp 2.x** | **`from mcp.server.mcpserver import MCPServer`**（FastMCP 已改名） |

而 Fay 自带的那个能用的 server（`fay_player_knowledge_..._mcp_server.py`，**2156 行**）
用的是**手写 stdio 协议**（`read_framed_message` / `write_response`），所以不受版本影响。

**解法**：本项目用 mcp 2.x 的 `MCPServer` + `@mcp.tool()` 装饰器（代码量小得多）。

**错误日志位置**：`Fay-main/logs/mcp_stdio_python.EXE.log` —— **排查 MCP 连接失败先看这里**，
它记录了子进程的完整堆栈（HTTP 接口只回一句笼统的"连接失败"）。

**状态**：✅ 已解决

### 问题 4：Fay 的 `/api/send` 只收 form data，不收 JSON

**现象**：用 JSON body 发消息，接口回 `{"result":"error","message":"未提供数据"}`，
消息根本没进对话。

**根因**：`gui/flask_server.py` 的 `api_send` 读的是 `request.values.get('data')`
（= query string + form data），**不含 JSON body**。

**正确发法**（注意是表单，且内容是 JSON 字符串）：

```powershell
$inner = @{ username = "User"; msg = "问题" } | ConvertTo-Json -Compress
Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/send" -Method Post -Body @{ data = $inner }
```

> 教训：**别把响应 Out-Null 掉**。我第一次就是没看返回，白等了一轮。

**状态**：✅ 已解决
