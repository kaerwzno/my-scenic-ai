# 知识库自进化：数据接口与页面规划

> 2026-09-25 重写。上一版的方案建立在一个不可靠的指标上（向量距离），这一版换掉。

---

## 一、先说清楚上一版为什么不行

上一版的链路是：**命中率低 → 提示补知识**。但实测发现判断缺口的三个环节**全是"事后从日志里猜"**：

| 环节 | 手段 | 实测问题 |
|---|---|---|
| 判断缺口 | 向量距离阈值 | **既误伤又放过**：0.35 会把「五明桥横跨哪片水域」这种答案就在库里的问题判成未命中；0.55 会把「停车场收费」这种库里 0 块知识的问题判成命中 |
| 判断拒答 | 关键词匹配 | **召回率 29%**（7 道缺口题只识别出 2 道）——数字人实际说的是「没查到」「没找到」，而词表里只有「无法确认」「没有可靠」 |
| 问题归类 | 关键词规则 | **14% 的问题掉进「其他」** |

**用猜出来的数据指挥"补什么知识"，结论必然错。**

而且有个关键事实：**数字人本身的表现是对的**——7 道缺口题全部如实说"没查到"、零编造。
**问题不在数字人，在我们观测它的手段。**

## 二、新的架构：把"猜"换成"申报"

```
┌─ 在线（每次对话）──────────────────────────────┐
│ 数字人答题                                     │
│   ├─ 有依据 → 按置信度组织语气                 │
│   └─ 答不上来 → 调用 report_unknown(topic, q)  │  ← 关键：主动申报
└────────────────────────────────────────────────┘
                    ↓ 落盘 unknown.jsonl
┌─ 离线（定期，比如每天）───────────────────────┐
│ 分析 agent（大模型）                            │
│   输入：申报记录 + 对话原文 + 现有知识目录      │
│   输出：缺口清单 + 冗余清单 + 质量诊断（JSON）  │
└────────────────────────────────────────────────┘
                    ↓
┌─ 管理端「知识分析」页 ─────────────────────────┐
│ 三个区块：要补什么 / 要降什么 / 回答质量        │
│ 管理者审核 → 接受或驳回 → 补知识 → 回归验证     │
└────────────────────────────────────────────────┘
```

**分工的核心**：

| 谁 | 干什么 | 为什么是它 |
|---|---|---|
| 数字人（在线）| 答不上来时**申报** | 只有它自己知道"我答不上来"，这是语义判断，不是统计推断 |
| 分析 agent（离线）| **归纳主题、写建议、找冗余** | 这是归纳和写作，大模型擅长；它不是判据 |
| 管理者 | 审核 + 决定补什么 | 红线：知识写入必须人工审核 |

## 二·五、agent 到底干什么：七项职责

先纠正一个我自己前面放错的位置：**判断"答不上来"不需要 agent**——数字人在线就能判断
（它自己知道答不上来，这是语义判断，不是统计推断）。让 agent 去做"归纳主题"这种活是浪费，
申报时已经带了 topic，聚合是免费的分类汇总。

**agent 的价值在"知识沉淀与重构"**，具体七项，分三类：

| 类 | 职责 | 解决什么 | 优先级 |
|---|---|---|---|
| **补什么** | ① **问法扩展** | 命中率——申报只给一种问法，扩展成一组 | ⭐⭐⭐ |
| | ② **内容提炼** | 沉淀对话里长出来的知识 | ⭐⭐⭐ |
| | ③ **人群画像 → 缺口** | 发现"问题计数少但需求真实"的缺口 | ⭐⭐ |
| **怎么组织** | ④ **更新交叉引用**（图谱同步）| 向量库和知识图谱脱节 | ⭐⭐ |
| | ⑤ 结构重构（冗余/拆分/降级）| 长期质量 | ⭐ |
| **怎么保持正确** | ⑥ **矛盾检查**（存量 + 增量）| 数据源冲突被游客发现 | ⭐⭐⭐ |
| | ⑦ **时效性核对** | 票价/开放时间过期 | ⭐⭐ |

### ② 内容提炼：什么叫"知识沉淀"

**具体例子**（真实对话记录）：

```
用户问：灵山有什么纪念品值得买？
知识库：没有纪念品信息（0 块）
数字人答：「……可以考虑五印坛城的藏香制作体验，能亲手做一份藏香，比较适合当作纪念」
```

最后那句**是它自己推出来的**——用「五印坛城·藏香制作体验」这条知识 + 常识推理。
但**这条答案随对话消失了**：下次另一个人问同样的问题，检索还是命中不了，
又要重新推理一遍，**而且可能推得不一样**。

**这就是"知识没有沉淀"**。agent 该抓的正是这个：

```
对比「回答」与「检索到的块」→ 发现回答里有检索结果没有的内容
→ 提炼成候选知识块（标注来源：对话提炼，带日期）
→ 待人工审核
```

这类知识**不是资料包里本来就有的，是在服务过程中长出来的**——这才是"复利型知识资产"。

### ③ 人群画像 → 缺口：解决"样本不足"判不出结论的问题

缺口有两种视角，交叉才完整：

| 视角 | 看什么 | 例子 |
|---|---|---|
| **问题类别** | 哪一类**问题**答不上来 | 交通停车、餐饮住宿 |
| **人群画像** | 哪一类**人**的需求满足不了 | 行动不便者、带娃家庭 |

**为什么必须有第二个视角**：实测「老人与无障碍」只被问了 2 次，按最小样本门槛
只能显示"样本不足、不下结论"。但如果画像显示**有 8 位游客都提到腿脚不便**，
这个需求是真实且重要的，**不该因为"被问次数少"被忽略**。

**画像提供了第二个证据来源。**

### ④ 更新交叉引用：我们的两套知识库会脱节

现在有**两套独立的知识库**：向量检索（130 块）和知识图谱（628 实体 / 813 关系），
**它们是分开建的**。后果：**补了新知识，图谱不会更新**——
补了"停车场收费"，图谱里没有"停车场"这个实体，也建不了它和"灵山胜境"的关系。

agent 该干：补知识的同时抽取实体和关系，**同步写进图谱**。这才是真正的"更新交叉引用"。

### ⑥ 矛盾检查：我们已经有两条真实案例，但是人工发现的

| 冲突 | 来源 A | 来源 B |
|---|---|---|
| 九龙灌浴总高/耗铜 | 27.2 米 / 180 吨 | 27.5 米 / 260 吨 |
| 灵山大佛铜壁板 | 2000 块铸铜面板 | 1560 块铜壁板 |

**这两条是人工翻资料时撞见的**，系统没报警。agent 可以自动做两件事：

- **存量检查**：扫知识库，找同一事实的多个版本
- **增量检查**（更重要）：**新知识进来时，检查它和已有知识是否冲突**

第二条特别关键：如果有人补了"停车费 10 元"，而另一处写着"15 元"，
**必须当场发现**，不能等游客问出来。

### ⑦ 时效性核对：票价这种事，写错了就是在骗人

**游客问"门票多少钱"，如果知识库写的是去年的价，那就是在骗人。**

现在知识库没有"这条知识什么时候生效"的概念。agent 该干：

- 给知识块打**时效标记**（票价/开放时间/演出场次 = 时效性高）
- 定期提醒核对："票价这条已经 6 个月没核对了"
- 有新资料时自动对比并提示冲突

### 字段设计说明

| 字段 | 为什么必须有 |
|---|---|
| `questions`（原始问题数组）| **每一条建议都要能看到原始问题**。管理者据此判断是不是真缺口，而不是信一个数字 |
| `evidence`（证据）| 说明"为什么判断这是缺口"——申报了几次、距离多少、知识库有几块。可复算 |
| `status`（pending/accepted/rejected/done）| 审核状态机。**驳回也要记**，否则下次 agent 还会提同一条 |
| `redundant` | 自进化的另一半（降级）。你之前说"降级先留着不处理"，所以先出清单、不自动执行 |
| `quality.by_category` | 这是"回答质量"视图，**它的用途是发现检索问题，不是发现缺口** —— 所以和 `gaps` 分开 |
| `errors` | 系统故障独立一栏，绝不能混进缺口（这个坑踩过三次） |
| `personas` | **人群视角的缺口**。它解决"问题计数少但需求真实"的情况——「老人与无障碍」只被问 2 次（样本不足），但 8 位游客提到腿脚不便。`note` 字段专门解释"为什么这条计数少却要优先处理" |
| `conflicts` | 同一事实的多个版本。**存量扫描 + 增量检查都要有**：新知识进来时和已有知识比对，冲突要当场发现，不能等游客问出来 |
| `stale` | 时效性内容（票价/开放时间/演出场次）。`volatility` 标时效等级，用来决定核对频率。**写错了就是在骗人** |

## 四、管理端「知识分析」页的新结构（从 9 块精简到 4 块）

### 原则：每一块都要回答"我该做什么"

| 区块 | 回答什么 | 数据源 | 操作 |
|---|---|---|---|
| **① 要补什么** | 该补哪一块知识 | `gaps` | 接受 / 驳回 / 标记已补 |
| **② 要降什么** | 哪些知识没人问 | `redundant` | 接受 / 驳回（先只出清单） |
| **③ 回答质量** | 哪一类答得不够稳 | `quality` | 无（诊断用） |
| **④ 系统故障** | 有没有报错 | `errors` | 无（条件显示） |

### 被合并 / 搬走 / 删掉的

| 原来的块 | 怎么处理 | 为什么 |
|---|---|---|
| 拒答分析·知识缺口 | **合并进 ①** | 和「答不上来的问题」说的是同一件事 |
| 答不上来的问题 | **合并进 ①** | 同上 |
| 拒答分析·域外拒答（整张表）| **缩成一行计数** | 正确行为，不是缺口，不值得占一张表 |
| 知识缺口分析（按类别）| **改造成 ③ 回答质量** | 它诊断的是"检索准不准"，不是"缺不缺内容"——名字改对了，用途才不会跑偏 |
| 知识块使用情况 | **合并进 ②** | 它就是"该降级"的输入 |
| 热点查询 TOP15 | **搬到「数据看板」** | 看板数据，不属于知识分析 |
| 各知识库调用次数 | **搬到「数据看板」** | 同上 |
| 按景点看关注度 | 保留，放 ③ 下面 | 和"按类别"是互补视角（哪一类该补 vs 哪个景点该补）|

### 页面顶部的说明文字（要写清楚口径）

```
本页是「知识库自进化」的操作台。三块内容对应三件不同的事：

  要补什么 —— 数字人答不上来时会主动申报，这里按主题汇总。
             每条都附原始问题，你可以判断是不是真缺口。
             接受后会记入待办；补完知识请回来标记「已补」，便于回归验证。

  要降什么 —— 知识块很多但几乎没人问的内容，可以考虑降级或合并。

  回答质量 —— 这不是缺口判据，是诊断：哪一类的检索匹配得不够准。
             命中率 = 铁证率（相似度足够高），弱相关不计入。
             命中率低但知识块多 → 问题在检索，不在内容。
```

## 五、置信度：贯穿整条链路的一个新字段

你现在要的"给一个置信度"，落在这三个地方：

### 5.1 来源：余弦距离

我们**早就有这个原始数据了**，只是没用起来。

```
置信度 = 1 - 余弦距离        （再按阈值归一化，更直观）
距离 0.15 → 85%   距离 0.40 → 60%   距离 0.55 → 45%
```

### 5.2 用在提示词里（让模型校准语气）

| 置信度 | 该怎么说 |
|---|---|
| 高（≥85%）| "灵山大佛通高 88 米"（肯定语气）|
| 中（60–85%）| "资料里提到…，你可以参考" |
| 低（<60%）| "我这边没有查到确切信息" |

### 5.3 用在评估里（这是"重测"的核心价值）

重测时**按置信度分层出准确率**：

| 置信度档 | 样本 | 准确率 |
|---|---|---|
| 高 | ~108 | **?** |
| 中 | ~68 | **?** |
| 低 / 无 | ~3 | **?** |

**如果高置信档准确率明显高于中置信档，就说明置信度是校准的**——
这是论文里一个很强的结论：*系统不只给出答案，还给出可验证的置信度*。
反过来如果三档差不多，说明距离这个置信度不可信，得换判据。**这个实验本身就有价值。**

## 六、实施顺序

| # | 做什么 | 依赖 | 工作量 |
|---|---|---|---|
| 1 | 数字人**申报工具** `report_unknown` + 提示词 | 无 | 小 |
| 2 | **置信度**传进提示词 | 和 1 一起改 | 小 |
| 3 | 管理端**页面重构**成 4 块 | 1、2 | 中 |
| 4 | **分析 agent**（离线定期出 JSON）| 1、3 | 中 |
| 5 | **重测** → 按置信度分层出准确率 | 全部 | 中 |

**第 1、2 步现在就能做**，而且都要改 Fay 的提示词，适合一起做。

### 重测的两条纪律

1. **必须用同一批题**（就是那 172 条），否则没法对比。第一次的准确率是整个后续优化的基线。
2. **重测前先把「人工判定」列填了**——没有基线就证明不了改进。

## 七、这些在论文里怎么讲

**不要写成**"我们做了一个自动补知识的系统"——三个判断环节的失败率都有数据，站不住。

**应该写成**：

> 本文提出一种**可观测的拒答申报机制**，将知识缺口的发现从"依赖统计推断"
> （向量距离阈值、关键词匹配）转变为"由模型在语义层面明确申报并归类"，
> 并配套**回归验证**闭环：补入知识后以原问题集复测，验证缺口是否真正被填补。
> 系统同时输出**可校准的置信度**，并通过分层准确率验证其有效性。

这个说法有实测支撑：

- 三个"推断式"环节的失败率都有数据（距离 30% 不确定档、拒答漏检 71%、分类失败 14%）
- 数字人本身零编造（7/7 缺口题正确拒答）
- 申报机制是**可验证的**：申报了就该补，补完再测
