### ★ 两处刻意的设计

**1. 嵌入的文本 ≠ 存进库的文本**

| | 内容 |
|---|---|
| **嵌入用** | 字段拼接：`景点名 + 信息类型 + 标签 + 问法 + 正文` |
| **存库用** | **纯正文** —— 它是最终喂给 LLM 的东西，不该带标签 |

拼接是旧项目的技巧（"低成本字段加权"）：让"用户可能怎么问"预先进入向量，口语问法也能命中。

**2. metadata 字段名对齐旧项目检索层**

```python
# 必须和 vector_retriever._fact_from_metadata 读的字段名一致
source / scenic_name / spot_id / spot_name / info_type
tags / questions_json / priority / is_fact
# 本项目新增
protected / protect_reason / index_version
```

**字段名对不上 = 检索层读不到 = 复用白做。**

## 四、★ 第 7 题暴露的固有局限（重要）

```
问：拈花湾有什么好玩的？
答（检索结果）：拈花广场 · 位置 / 拈花广场 · 功能
期望：梵天花海、香月花街、五灯湖、鹿鸣谷…（拈花湾有哪些景点）
```

**这不是 bug，是向量检索的固有短板。**

| 问题类型 | 向量检索表现 | 原因 |
|---|---|---|
| **精确问题**（"大佛多高"） | ✅ 很好 | 语义对应一个具体的块 |
| **概览问题**（"有什么好玩的"） | ❌ 无力 | 需要**跨块聚合**，而不是找最像的一块 |

而"拈花湾包含哪些景点"这种**包含关系**，恰恰是**知识图谱的主场**。

**这正好印证了用户的判断：图谱必须做增强问答，否则就是摆设。**

### ✅ 已解决（2026-09-25）：图谱增强问答插件

新增 `plugins/kb-graph/`（图谱 MCP 插件），暴露 `graph_query` / `graph_stats`。
逻辑移植自旧项目 `apps/graph_api/views.py` 的 `_rank_nodes` / `_collect_graph_evidence`。

**效果对比（同一个问题）**：

| | 只用向量检索 | 加了图谱检索 |
|---|---|---|
| 问「拈花湾有哪些景点值得逛」 | 只列出 **3 个**（拈花广场、五灯湖、香月花街） | 列出 **7 个**（拈花广场、香月花街、拈花堂、拈花塔、梵天花海、五灯湖、鹿鸣谷） |

**Fay 能自主路由**：概览类问题走 `graph_query`，具体事实问题走对应景区的 `*_query`。

#### 过程中的两个发现

| # | 发现 | 处理 |
|---|---|---|
| 1 | **`<SEP>` 未清理**：LightRAG 图谱描述里用 `<SEP>` 分段，原样输出会污染文本 | 把 `<SEP>` 也纳入分隔符清洗 |
| 2 | **单字重叠导致误命中**：问「今天天气怎么样」时，`天井`/`飞天` 只因共用一个"天"字就被选中，域外问题也能捞出无关实体 | 要求**至少两个字符重叠**（或实体名整体出现在问题里）；改完后域外问题正确拒答 |
| 3 | **agent 的工具选择不完全可靠** | 第一版描述里图谱工具没抢过向量工具，Fay 仍选了向量检索。把"**必须用本工具的场合 / 不要用的场合**"写进 `plugin.json` 的 description 后，路由才正确 |

> 教训：**给 agent 用的工具，描述就是"路由策略"**。
> 描述写含糊，agent 就会选错工具；要显式写清"什么时候必须用它、什么时候不要用"。

### 三层解法（按需要逐步加）

| 层 | 做法 | 能解决 |
|---|---|---|
| 1 | 现有向量检索 | 精确问题 |
| 2 | **图谱检索**（`query_graph`） | "X 包含哪些 Y"这类关系问题 |
| 3 | **由 Fay 的 judge 决定用哪个工具** | 概览问题走图谱，事实问题走向量 |

**第 3 层才是"Agent 工作流"相对"固定流水线"的真正价值。**
