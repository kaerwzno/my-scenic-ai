# 灵灵 · 陪伴数字人

> **一句话定位**：一个**有记忆、会主动**的景区导览数字人——不是"你问我答"的问答机器人，而是一个会记住你、认得你、主动关心你的导游伙伴。

项目根目录：`D:\PROJECT\scenic_ai\重构数字人`

## 一、项目定位

### 1.1 我们要做的是什么

| | 传统景区问答机器人 | **本项目** |
|---|---|---|
| 交互模式 | 用户问 → 系统答 | **双向**：用户问会答，也会**主动开口** |
| 记忆 | 无，每次都是陌生人 | **长期记忆**：记得你上次说过什么 |
| 关系 | 一次性的工具 | **持续演进**：用得越久越懂你 |
| 人格 | 无 | **有人格、有语气、有关系** |

### 1.2 目标场景与验证场景（重要）

这个区分会影响每一个设计决策，必须写在最前面：

| | 场景 | 角色 |
|---|---|---|
| **验证场景** | 景区导览（灵山胜境 / 拈花湾） | **练手场**——知识可验证、后果可承受 |
| **目标场景** | **孤独症儿童陪伴** | **终点**——高价值、高情感、高安全要求 |

**为什么先用景区验证**：

- 景区知识是**封闭且客观**的（票价、高度、开放时间都有唯一正确答案），可以量化准确率
- 问错了后果轻，适合趟坑
- 已有的 304 条结构化知识 + 评测系统可以直接复用

**但必须清醒**：景区场景**验证不了**陪伴场景真正的难点——

| 能力 | 景区能验证吗 |
|---|---|
| 知识库可插拔、Agent 工具调用、数字人渲染、多模型分层 | ✅ 能 |
| 长期记忆与跨会话召回 | ❌ **验证不了**（游客不会回来第二次） |
| 用户画像与关系演进 | ❌ **验证不了** |
| 情绪表达与安抚 | ❌ **验证不了** |
| 安全护栏（说错话的后果） | ❌ **验证不了** |

**因此**：架构上必须**为陪伴场景预留通路**，不能做成一个"只能答景区问题"的系统。
每个模块完成后都要问一句：**"它能不能直接用在陪伴场景？"** 不能的，要么改设计，要么明确记为"将来要重做"。

### 1.3 不做什么（边界）

- ❌ 不做"治疗"自闭症的宣称。数字人是**辅助工具**，不是医疗手段。
- ❌ 不做无人审核的自动知识写入（详见 §7 风险）。
- ❌ 不追求"C 端百万并发"——本定位是**少数用户、长期关系**。
- ❌ 不为景区定制死逻辑——知识库必须是可插拔的插件。

## 二、技术选型

### 2.1 为什么基于 Fay

**核心原因**：目前开源项目里，**只有 Fay 同时具备「Agent 内核」和「数字人接口协议」**。

| 方案 | Agent 工作流 | 可插拔知识库 | 数字人接口 | 长期记忆/反思 |
|---|---|---|---|---|
| **Fay** | ✅ 认知流 + judge | ✅ MCP | ✅ WebSocket + 动作语义 | ✅ 斯坦福 Generative Agents |
| LangGraph | ✅ | ⚠️ 自己接 | ❌ | ❌ |
| Dify / FastGPT | ✅ | ✅ | ❌ | ⚠️ |
| LiveTalking 等数字人项目 | ❌ | ❌ | ✅ | ❌ |

**Fay 的设计文档原话**（`Fay-main/docs/fay_vs_harness_memory.md`）：

> Fay 的目标是承载一个**会陪伴用户多年、会跨多种场景工作、会随时间成长**的数字人主体。
> 记忆要做的不是"帮 agent 别忘事"，而是**让数字人成为一个有人格、有关系、有时间纵深的存在**。

**这正是我们要做的事。**

### 2.2 之前三个"风险"为什么在这里不成立

在"匿名游客高并发"的假设下，Fay 有三条不匹配；换成"少数用户长期陪伴"后全部化解：

| 风险 | 在陪伴定位下 |
|---|---|
| C 端高并发不匹配 | ✅ 消失——本定位就是少数用户 |
| Agent 自主性 vs 1.8 秒延迟 | ✅ 消失——陪伴场景"答得准、记得住、有温度"远比"答得快"重要 |
| 双状态一致性 | ⚠️ 仍在，但用户少，可控 |

### 3.2 职责划分

| 谁 | 是什么 | 状态 |
|---|---|---|
| **Fay 内核** | 数字人的**人格 + 记忆 + 思考 + 主动** | 直接采用 |
| **知识库插件（MCP）** | 数字人的**技能**（景区知识是第一项技能） | **要开发** |
| **数字人身体** | 渲染端（Live2D / LiveTalking / 3D） | 部分复用旧项目 |
| **自进化 Agent** | 数字人的**成长机制** | **要开发** |
| **小程序** | 数字人的**入口** | 复用旧项目，改造对接 |
| 旧项目的 RAG 代码 | 某项技能的**具体实现** | 复用，封装进插件 |

### 3.3 关键技术契约

| 契约 | 位置 | 说明 |
|---|---|---|
| 知识库插件 | MCP（stdio / SSE），MCP 管理服务 **5010** | Fay 主动调用插件 |
| 数字人驱动 | **WebSocket 10002** | 插件主动连 Fay，Fay 推送文本+音频+动作语义 |
| 动作语义 | `Action{code, behavior, affect, intensity, priority}` + `Sentiment` | Fay **只输出语义**，不输出 `MotionNo` 等实现细节；各渲染端自己映射 |
| 记忆服务 | `core/memory_service.py` 的 `remember / search / get_reflections / get_active_rules / get_user_profile` | 外部可读写 |
| 对外接口 | HTTP 5000（`/api/send`、`/api/get-msg`、`/v1/chat/completions`） | 小程序接入用 |

## 六、验收点

> 每个验收点必须**可复现**：写清"怎么验"和"通过标准"，验完把结果记进 `docs/acceptance.md`。

### 第 1 期 · 地基

#### ✅ 验收点 1：数字人能对话

- **怎么验**：启动 Fay，连续进行 3 轮文字对话
- **通过标准**：3 轮都返回通顺回答；启动日志出现 `embedding 服务预热完成`；`samples/` 有音频产出
- **状态**：✅ 已达成（2026-09-25，Fay 首次跑通）

#### ✅ 验收点 2：记忆跨会话生效 ★核心

- **怎么验**：
  1. 会话 A：告诉它"我腿脚不方便，别推荐爬台阶的路线"
  2. **完全结束会话 A**（重启 Fay 或切换新会话）
  3. 会话 B：只问"推荐个路线"，不提腿脚的事
- **通过标准**：会话 B 的回答里**体现了"避免爬台阶"这个约束**
- **量化指标**：准备 10 条记忆项，跨会话召回率 ≥ 80%
- **为什么这是核心**：这一条过了，才证明"陪伴"成立；不过，就只是换了壳的问答机器人

### 第 2 期 · 主动能力

#### ✅ 验收点 3：数字人能主动开口 ★核心

- **怎么验**：
  1. **定时主动**：静置一段时间，观察是否主动发起对话
  2. **事件主动**：模拟"用户到达某景点"，观察是否主动讲解/提醒
- **通过标准**：能收到主动消息，且**内容与上下文相关**（不是固定话术）
- **反例**：如果主动消息是写死的字符串，**不算通过**

### 第 3 期 · 可插拔

#### ✅ 验收点 4：知识库可插拔

- **怎么验**：
  1. 装「灵山」知识插件 → 问灵山问题 → 答案来自灵山语料
  2. 装「拈花湾」知识插件 → 问拈花湾问题 → 答案来自拈花湾语料
  3. 两个插件同时启用 → 混合提问
- **通过标准**：**改插件不改代码**；停用插件后相关问题会拒答（证明没有用模型脑补）

#### ✅ 验收点 5：数字人形象可切换

- **怎么验**：同一段文本，切换 ≥2 种形象播报
- **通过标准**：
  - ≥2 个形象可用（如 Live2D 古风 + LiveTalking 写实）
  - 口型跟随音频
  - **动作语义正确映射**（Fay 输出 `behavior=invite` → 本地对应动作）
- **注意**：Fay 侧不需要为换形象改任何代码

### 第 4 期 · 自进化

#### ✅ 验收点 6：自进化闭环跑通 ★核心

- **怎么验**：
  1. 问一个知识库确实没有的问题 → 被拒答并**记录**
  2. 运行缺口分析 → 产出候选知识
  3. **人工审核**通过
  4. 写入知识库（走 MCP 工具）
  5. 再问同一个问题 → **能正确回答**
- **通过标准**：完整闭环跑通**至少一次**，且**审核环节真实存在**（不是走过场）
- **反例**：如果模型生成的内容未经审核直接入库，**不算通过**

### 最终 · 端到端

#### ✅ 验收点 7：完整演示走通

- **怎么验**：模拟一个新用户完整流程

  ```
  第一次见面（冷启动采集偏好）
    → 建立记忆
    → 结束会话
    → 新会话中被记住
    → 数字人主动关怀
    → 问景区问题（知识库回答）
    → 切换形象
    → 明确说出记忆里存的偏好
  ```

- **通过标准**：全流程无中断、无人工干预

## 七、已知风险与红线

### 7.1 三条红线（不可突破）

| # | 红线 | 原因 |
|---|---|---|
| **1** | **知识写入必须有人工审核** | 无审核的自动写入 = 把幻觉固化成事实。陪伴场景后果更严重 |
| **2** | **不做"治疗"宣称** | 涉及儿童与医疗伦理边界。定位是辅助工具 |
| **3** | **记忆必须可查看、可纠正、可删除** | 长期记忆涉及敏感信息，用户/监护人有权知晓和控制 |

### 7.2 需要解决的技术问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | **冷启动** | 第一次见面什么都不知。**旧项目登录页的"偏好选择"可升级为初识流程** |
| 2 | **记忆管理粒度太粗** | Fay 只有"删整个用户"和"清空全部"，缺"查看/纠正单条记忆" |
| 3 | **"保留所有记忆"需修正** | 事无巨细全存会导致检索噪声。应改为"**保留所有重要记忆 + 可检索**"，用 `importance_score` 分级 |
| 4 | **身份识别** | 换设备/换入口后，怎么确认还是同一个人 |
| 5 | **延迟不可测** | Agent 每次多一次 judge 调用，需实测 |
| 6 | **双状态一致性** | Fay 的记忆库 vs 自己的业务库 |
