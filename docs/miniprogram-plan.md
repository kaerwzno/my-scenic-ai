# 小程序端方案：多形象数字人 + 多模态输入

> 记录 2026-09-25 的设计讨论。定位：个性化陪伴游客的景区数字人导览。

---

## 〇、三条已定的决策

| # | 决策 | 含义 |
|---|---|---|
| **D1** | **换形象不换记忆** | 用户换了一个数字人形象，之前的记忆全部保留。实现上：Fay 的 `username` 不变，只改用户档案里的 `avatar_id` |
| **D2** | **小程序端先做多形象** | 用户能在小程序里选形象；管理端同步要有形象管理页 |
| **D3** | **形象 / 音色 / 人格三者解耦** | 形象与音色归数字人层（用户可选），人格归管理端（用户不可改） |

### 为什么 D1 选「换皮不换人」

景区场景里，游客下次来应该还认得出「灵灵」。更重要的是终极场景——**孤独症陪伴需要一个稳定、可预期的对象**，形象越多样，对这类用户越可能是干扰。

所以产品定位是：**选择权在用户，稳定性由系统保证**。用户选定一个形象后就长期用它，而不是每次随机换。

技术上 D1 几乎不额外花钱：Fay 的记忆按 `username` 存，只要换形象时不换 username，记忆天然延续。这一点让「多形象」从一个架构难题变成了一个数据字段。

## 一、整体链路

```
┌─ 小程序端 ────────────────────────────────────────────┐
│  打字  ──────────────────────────┐                    │
│  语音  录音 → 音频文件 ──→ ASR ──┤                    │
│  拍照  图片文件 ──→ 多模态理解 ──┤                    │
│  视频  抽帧 → 图片 ─→ 多模态理解 ┘                    │
└──────────────────────┬────────────────────────────────┘
                       ▼
              ┌─────────────────┐
              │  BFF / 网关      │  鉴权 · 用户档案 · 媒体上传
              │ （新增，必做）    │  模型调用 · 形象配置下发
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │  Fay 内核        │  记忆 · 人格 · 主动 · 工具调用
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │  知识库插件(MCP) │  灵山 / 拈花湾 / 图谱
              └────────┬────────┘
                       ▼
              回复文本 + Action{behavior, affect, intensity}
                       ▼
              ┌─────────────────┐
              │  TTS 合成音频    │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │  数字人驱动      │ 小程序：分层 2D + 口型
              │                 │ 管理端：Live2D / 视频驱动
              └─────────────────┘
```

### 为什么中间必须有 BFF

不能让小程序直连 Fay，三个硬原因：

1. Fay 的 `/api/send` 收 form-data、**没有鉴权**，暴露给小程序等于把大脑开放到公网；
2. Fay 的用户就是明文字符串 `username`，没有账号体系，小程序必须有自己的一套；
3. 媒体上传、ASR、视觉、TTS 这些调用都需要一个能拿 API Key 的地方——**Key 绝不能进小程序包**（小程序包可被反编译）。

## 二、多模态输入：不要 all-in 一个 omni 模型

你提到 omni，方向对，但**不建议把所有模态都塞给它**。这三路的性质完全不同：

| 模态 | 性质 | 适合的做法 |
|---|---|---|
| 打字 | 纯文本 | 直接转发 |
| 语音 | 一次性的「转文字」任务 | 文件上传 + ASR，不需要长连接 |
| 图片 | 一次性的「看懂」任务 | 视觉模型，便宜快 |
| 视频 | 抽 3~5 帧通常就够 | 抽帧 + 视觉模型 |

omni 的价值在两个地方：**一个模型同时吃图和文**，以及**实时语音对话**。前者我们能用上，后者是二期的事（小程序维持 realtime 音频长连接，稳定性和成本都还没验证）。

### 关键设计：多模态只负责「翻译成文字」，不负责回答

```
用户发一张照片
   ▼
多模态模型 → 「这是灵山大佛，游客站在登云道下方仰拍」
   ▼
作为一条带描述的用户消息，发给 Fay
   ▼
Fay 结合记忆 + 知识库回答
```

**为什么不让 omni 直接回答景区问题**：它接不到我们的知识库（除非给它开工具调用，那就等于把 Fay 的活重做一遍），而且回答无法被埋点、无法被缺口分析统计。让它只做「翻译」，架构简单、可追责、所有回答都走同一条链路。

### 模型选型（都来自你那份百炼清单）

| 用途 | 首选 | 备选 | 说明 |
|---|---|---|---|
| 语音转文字 | `qwen3-asr-flash` | `fun-asr-flash`、`qwen-audio-3.0-asr-flash` | 非流式，文件上传即可 |
| 图片理解 | `qwen3.8-omni-flash` | `qwen3-vl-flash` | omni 一个模型吃图文，比 VL 划算 |
| 视频理解 | 抽帧 + `qwen3.8-omni-flash` | `qwen3.5-omni-plus` | 抽帧比直接吃视频省钱可控 |
| 语音合成 | `qwen3-tts-flash` | `qwen3-tts-instruct-flash`（可指定语气）| instruct 版能给每个形象定语气 |
| 音色克隆 | `qwen3-tts-vc` | — | 给每个形象配专属音色 |
| 形象素材 | `qwen-image-3.0-pro` | `z-image-turbo` | 解决「美术素材从哪来」 |
| 实时语音（二期）| `qwen3.8-omni-flash-realtime` | `qwen-audio-3.0-realtime-plus` | 暂缓 |

## 三、TTS + 口型驱动：一个必须提前知道的坑

理想链路是：音频进来 → 实时分析音量 → 驱动嘴型。**但小程序做不到实时音频分析**——`InnerAudioContext` 不给你音频数据，只有个粗粒度的 `onTimeUpdate`（约 250ms 一次，太慢）。

### 解法：把音量包络预先算好，随音频一起下发

```
BFF：TTS 得到 wav
   → 解码成 PCM
   → 每 50ms 算一次 RMS 音量
   → 归一化到 0~1，做平滑（attack / release）
   → 得到 [0.0, 0.12, 0.55, 0.83, 0.31, ...] 这样一个数组
   ▼
下发：{ audioUrl, envelope: [...], intervalMs: 50 }
   ▼
小程序：音频播放 + 本地计时器按 envelope 逐步设置嘴部开合
   ▼
音画同步由同一份时间轴保证，不依赖小程序的音频能力
```

两个工程细节：

1. **必须做平滑**。直接用原始 RMS，嘴巴会高频抽搐。要做 attack（快速张开）和 release（缓慢闭合）的不对称平滑。
2. **首尾要补静音段**。音频开头通常有几十毫秒空白，不处理的话嘴巴会先动一下再说。

口型映射用 0~1 的开合度就够，不需要音素。这个值直接对应 Live2D 的 `ParamMouthOpenY` 语义（见 Fay 的《Live2D 模型制作要求》），所以**同一份包络既能驱动分层 2D，也能驱动 Live2D**。

### 三档口型方案

| 方案 | 做法 | 效果 | 成本 |
|---|---|---|---|
| **A（先做）** | 音量包络 → 嘴部开合 0~1 | 能看，够用 | 低 |
| B | 音素/时长对齐 | 精确 | 高（要强制对齐工具）|
| C | wav2lip / musetalk 出视频 | 最真 | 高（要 GPU），且小程序放视频流量大 |

## 四、多形象的落地

### 4.1 形象配置：一份 `avatars.json`

沿用 `categories.json` 那套思路——**可编辑、改完立即生效、管理端可视化**。

```json
{
  "avatars": {
    "lingling": {
      "name": "灵灵",
      "scenic": "lingshan",
      "tagline": "温柔的景区小导游",
      "voice": {"model": "qwen3-tts-flash", "voice_id": "..."},
      "render": {
        "type": "2d_layered",
        "layers": {
          "body": "lingling/body.png",
          "eyes_open": "lingling/eyes_open.png",
          "eyes_close": "lingling/eyes_close.png",
          "mouth": ["m0.png", "m1.png", "m2.png", "m3.png", "m4.png"]
        }
      },
      "persona_hint": "温柔、语速慢、多用短句",
      "enabled": true,
      "order": 1
    }
  }
}
```

字段职责要说清：

- `voice` / `render` / `tagline` —— 用户可感知、管理端可改
- `persona_hint` —— 只是**给管理端的备注**，不改 Fay 的人格。人格（name / goal / 风格）在 Fay 的 `config.json` 里，用户改不了

### 4.2 用户的选择存哪

```
BFF 用户档案表：user_id → avatar_id
        ↓
换形象 = 改这一个字段
        ↓
Fay 的 username 不变 → 记忆、偏好、行程全部保留（这就是 D1）
```

同时把这件事写进 Fay 记忆（发一条普通消息即可，比如「用户把形象换成了小沙弥」），这样数字人自己「知道」这件事，下次可以自然提到。这也让管理端能看到「哪个形象最受欢迎」。

### 4.3 小程序端怎么渲染分层立绘

用 `<canvas type="2d">`，不用 WebGL：

```
每帧绘制顺序：body.png → eyes（按眨眼计时器切换）→ mouth（按 envelope 选一张或缩放）
```

眨眼用一个自己维护的随机计时器（3~5 秒眨一次），跟音频无关。

**为什么不用 Live2D**：Cubism Core 是 wasm + 依赖 DOM 的运行时，搬到小程序要改一堆东西，风险高。分层 2D 用小程序原生 canvas 就能跑，且素材用图像生成模型就能出。Live2D 留给网页端和管理端演示。

### 4.4 管理端形象管理页

和「分类规则」页同一个模式：

- 形象列表（上架状态、排序、适用景区）
- 上传素材 / 在线预览
- 试听音色
- 编辑 `avatars.json`（或表单式编辑）
- 看每个形象被选了多少次（数据从 BFF 用户档案统计）

## 五、分阶段实施（每一步都能单独验收）

| 阶段 | 做什么 | 验收标准 |
|---|---|---|
| **0** | BFF 骨架：用户身份 + 把小程序消息转发给 Fay + 轮询取回复 | 小程序发一句，能收到 Fay 的回答 |
| **1** | 形象池 + 选择页 + 静态立绘显示 | 能选 2 个形象，切换后头像跟着变，**记忆还在** |
| **2** | TTS + 音量包络 + 口型动画 | 数字人说话时嘴在动，音画不错位 |
| **3** | 语音输入（录音 → ASR → 提问） | 按住说话，松手后能听到回答 |
| **4** | 图片理解（拍照 → omni → 带描述提问） | 拍灵山大佛，它能说出这是什么 |
| **5** | 管理端形象管理页 | 管理端能上架/下架/排序形象，小程序刷新后生效 |
| **6（二期）** | 实时语音 / 视频输入 / 视频驱动 | — |

建议顺序的理由：**先让「能听能看能说」跑通，再做花哨的**。阶段 1、2 就能出一个能演示的版本，阶段 3、4 是锦上添花。

## 六、必须提前知道的四个风险

1. **最大的障碍是美术素材，不是技术。** 每个形象要一套分层立绘（身体 / 眼睛 / 嘴型 5 张）。三个形象就是 20 多张图。解法：用 `qwen-image-3.0-pro` 批量生成，或先做「半身像 + 简单表情差分」的最小集，别一上来追求精细。
2. **形象版权。** AI 生成的形象要注意商用授权条款，景区对外发布时尤其要确认。
3. **小程序的音频能力受限**（见第三节）。所有「实时分析音频」的思路在小程序里都要改成「服务端预算好」。
4. **百炼 realtime 模型在小程序里的长连接稳定性未知。** 二期再碰，不要一上来就做成实时语音，不然演示当天掉线很难看。

## 七、这些设计在论文里怎么讲

三个可以写成贡献点的设计决策：

1. **形象与人格解耦** —— 换皮不换人，使「多形象」从架构难题降级为一个数据字段，同时保证陪伴关系的连续性（对孤独症陪伴场景尤其关键）。
2. **多模态只做翻译层** —— 把图/音翻译成文字后统一交给大脑，使所有回答都走同一条可埋点、可统计、可追溯的链路，而不是被多个模型分流。
3. **预计算口型包络** —— 在受限终端（小程序无法实时分析音频）上，用「服务端预算 + 时间轴下发」换取音画同步的确定性和低流量。

### 阶段 1：形象池（2026-09-25 完成）

| 产物 | 位置 | 说明 |
|---|---|---|
| 形象素材（5 个） | `assets/avatars/<id>/base.png` + `meta.json` | 1024×1024 PNG，占位用 |
| 生成脚本 | `scripts/gen_avatar_assets.py` | 走 DashScope 原生端点，key 从 Fay 的 `system.conf` 读 |
| 形象池配置 | `avatars.json` | 唯一数据源，由 `scripts/build_avatars_config.py` 汇总 |

五个形象：灵灵（古风·温柔）、小沙弥（古风·活泼）、智远（古风·儒雅）、灵犀（日系二次元·元气）、卡卡（Q 版卡通·安静）。

**踩到的两个坑（都会再遇到）**：

1. **百炼的 OpenAI 兼容端点没有图像生成路由。** `/compatible-mode/v1/images/generations` 返回 404。模型清单里能看到图像模型，但不代表这个端点开了对应路由。必须走 DashScope 原生端点 `api/v1/services/aigc/text2image/image-synthesis`，而且请求体格式也不同（`input.prompt` 而非 `prompt`）。可用模型实测为 `wan2.2-t2i-flash`、`wanx2.1-t2i-turbo`；`z-image-turbo`、`wan2.7-image` 在这个端点上不被接受。
2. **锚点必须跟着形象走，不能全局一份。** Q 版是二头身，脸占画面比例比半身像大得多，沿用半身像的锚点会把嘴画到脖子上。所以 `meta.json` 里每个形象各存一套 `anchors`，卡卡单独用 `ANCHORS_Q`。

### 阶段 0：BFF 骨架（2026-09-25 完成）

| 接口 | 用途 |
|---|---|
| `GET /api/health` | 自检（含 Fay 可达性、形象数） |
| `GET /api/avatars` | 形象池（只返回已上架的，按 order 排序） |
| `GET /api/assets/avatars/<path>` | 形象素材下发 |
| `GET /api/user/<user_id>` | 用户档案（当前形象、对应的 Fay 用户名） |
| `POST /api/user/<user_id>/avatar` | **换形象**（不动 Fay username，记忆必然保留） |
| `POST /api/chat/send` | 转发用户消息给 Fay |
| `GET /api/chat/poll` | 轮询取回复（替代小程序的 WebSocket） |

端口 **5180**。数据落在 `miniprogram-api/data/`：`profiles.json`（用户档案）、`user_map.json`（app 用户 → Fay 用户名）。

**两条必须守住的规则**：

1. **`user_map.json` 里的映射一旦定了就不能改** —— 改了等于清空那个用户的记忆。演示账号特意映射到 `User`，好继承网页端已经聊出来的记忆（腿脚不方便、靛蓝色）。
2. **换形象只改 `profiles.json` 里的 `avatar_id`** —— 实测验证：切换前后 `fay_user` 都是 `mp_visitor001`，记忆链路未受影响。

**测试模式**：环境变量 `FMP_NOTIFY_FAY=0` 会关掉「换形象写进 Fay 记忆」这个动作。跑别的脚本时开着它会插话，所以两个脚本并行时要关。

### 阶段 1 客户端：小程序页面（2026-09-25 完成）

原生小程序（和旧项目保持一致，不用 uni-app/Taro），位置 `miniprogram/`：

| 文件 | 作用 |
|---|---|
| `app.js` / `app.json` / `app.wxss` | 骨架、全局样式、页面注册 |
| `utils/api.js` | BFF 调用封装（地址在文件顶部 `BASE`） |
| `pages/avatar/*` | 形象选择页：卡片网格、点击选中、确认后建档并进聊天 |
| `pages/chat/*` | 聊天页：canvas 立绘 + 程序化嘴型 + 消息 + 轮询取回复 |

**跑起来要满足三件事**：

1. BFF 在跑（`miniprogram-api/app.py`，端口 5180）；
2. 微信开发者工具导入 `重构数字人/miniprogram` 这个目录；
3. 开发者工具里确认「详情 → 本地设置 → **不校验合法域名**」是勾上的——
   `project.config.json` 里虽然写了 `urlCheck: false`，但有时要在界面上再确认一次。
   真机调试要把 `utils/api.js` 里的 `BASE` 改成局域网 IP（如 `http://192.168.1.10:5180`），
   手机上的 `127.0.0.1` 指向的是手机自己。

**两个刻意的实现选择**：

1. **口型用程序化绘制，不是贴图**。按锚点位置画一个椭圆，纵向半径由开合度决定。
   因为文本生成图像做不出像素对齐的分层素材，硬做只会浪费时间。
   等有正式美术资源时换成贴 `mouth` 图层即可，**锚点和包络的接口不用改**。
2. **渲染状态不放进 `data`**。开合度每帧都在变，若走 `setData` 会以 60fps 触发小程序的数据通信，必然卡顿。所以放在页面实例上（`this.openness`），只在「正在说 / 在听你说」这种低频状态变化时才 `setData`。

**暂时用合成包络代替 TTS**：现在还没有 TTS，聊天页有个「试一下口型」按钮，
以及回复到达后按文字长度估算时长跑一遍合成包络——目的是**现在就能验证渲染链路**。
阶段 2 接上 TTS 后，把这段换成 BFF 下发的真实 `envelope` 即可，其余不动。

### 阶段 2 前置：订阅 Fay 的 WebSocket（2026-09-25 完成）

**为什么必须订阅**：Fay 有两条输出通道，口型和表情**只在第二条上**。

| 通道 | 内容 |
|---|---|
| 消息表 `fay.db` 的 `T_Msg` | 只有文字（BFF 原来读的是这个）|
| **WebSocket 10002**（HumanServer） | 文字 + **口型 Lips** + **表情 Action** + 音频 |

**订阅要做四件事**：

1. **连** `ws://127.0.0.1:10002`（注意不是 10000，那是面板服务）
2. **报身份**：连上后发 `{"Username": "<Fay用户名>"}`。服务端按这个字段过滤
   （`wsa_server.py` 的 `__producer_handler`：消息里的 `Username` 是谁就只发给谁）。
   **不发就默认是 `User`。**
3. **收** `{"Topic":"human","Data":{...},"Username":"..."}`
4. **缓存**：按用户存，供小程序的轮询接口取走

**三条实测得到的关键约定**：

1. **一条连接只能代表一个用户** → BFF 按用户懒开连接（谁开始轮询就给谁开），闲置 30 分钟断开。
2. **不要缓存 `Data.Value`** —— 那是 base64 音频，一条几百 KB，全存会吃光内存。
   小程序要的是**口型时间轴**，不是音频本身。只留 Lips / Action / Text。
3. **口型是分段推送的，必须等到 `IsEnd=1`**。
   实测：答案文字到达时只推了 1 段口型，6 秒后才凑齐 5 段。
   **客户端不能一看到 answer 就停止轮询** —— 这条不处理，嘴巴只会动第一句。

**实测样本**（问「灵山大佛有多高」）：

```
回答：灵山大佛通高 88 米，其中佛体部分 79 米，莲花瓣部分 9 米。如果把台基也算进去，总高是 101.5 米。
口型：5 段，共 127 段音素级数据
  · [21段] 我来帮你查一下，稍等…      action=neutral/wait   ← 占位段，客户端可跳过
  · [24段] 灵山大佛通高 88 米，
  · [24段] 其中佛体部分 79 米，
  · [40段] 莲花瓣部分 9 米。如果把台基也算进去，
  · [18段] 总高是 101.5 米。                              is_end=1
```

口型数据本身就是 Live2D 那套 viseme（`sil/PP/FF/TH/DD/kk/CH/SS/nn/RR/aa/E/ih/oh/ou`），
带毫秒时长，**比音量包络精确得多**——能区分闭唇（PP）、圆唇（oh/ou）、齿音（SS）。
所以之前设计的「服务端算音量包络」方案作废，直接用 Fay 给的 viseme。

对应代码：`miniprogram-api/ws_bridge.py`（订阅器）、
`GET /api/chat/poll` 现在会一并返回 `speech`（分段口型 + 表情）、
`GET /api/ws/status`（排查口型拿不到时先看它）。

### 阶段 2：小程序端接口型与表情（2026-09-25 完成）

**做法**：不用音量包络，直接用 Fay 的 viseme。

```
Fay 的 Lips: [{"Lip":"sil","Time":198},{"Lip":"kk","Time":33}, ...]
        ↓ 累加 Time 展开成时间轴
[{"t0":0,"t1":198,"open":0.0},{"t0":198,"t1":231,"open":0.35}, ...]
        ↓ 每帧按已过时间取当前项
画嘴（椭圆的开合度 + 横向宽度）
        ↓ 同一时间轴也在放音频
音画天然同步（同一份时长，不需要额外对齐）
```

**15 个 viseme 的映射表**（`pages/chat/index.js` 的 `VISEME`）：

| viseme | open | width | 说明 |
|---|---|---|---|
| `sil` | 0.00 | 1.00 | 静音，闭嘴 |
| `PP` | 0.02 | 0.95 | 双唇音 p/b，闭着 |
| `FF` | 0.15 | 1.05 | 唇齿音 f |
| `SS` | 0.20 | 1.10 | 齿音 s，嘴扁 |
| `TH`/`nn` | 0.25 | 1.00/0.95 | |
| `CH`/`RR` | 0.30/0.35 | 0.85 | 圆一点 |
| `DD`/`kk` | 0.35 | 1.00/0.95 | |
| `ih` | 0.40 | 1.05 | |
| `ou` | 0.50 | **0.68** | 嘟唇，横向明显收窄 |
| `E` | 0.55 | 1.08 | |
| `oh` | 0.65 | **0.78** | 圆唇 |
| `aa` | 0.90 | 1.05 | 低元音 a，张到最大 |

横向宽度（width）是关键：只改开合度的话，「o/u」和「a」看起来一样都是张嘴；
加上宽度就能区分**圆唇**（oh/ou 收窄）和**咧嘴**（aa/E/ih 展宽）。

**表情**：`action.affect` → 查表情图表 → 换底图。
7 张差分由 `scripts/gen_avatar_expressions.py` 用图像编辑模型从基础立绘派生。

**又修了一个必须修的坑**：Fay 给的音频 URL 是 `http://127.0.0.1:5000/audio/xxx.wav`，
小程序直连的话**真机上 127.0.0.1 指向手机自己**，音频放不出来。
所以 BFF 加了 `/api/audio/<文件名>` 做代理，并把这些 URL 改写成 BFF 自己的地址——
小程序只跟 BFF 说话，不绕过它去碰没有鉴权的 Fay。
