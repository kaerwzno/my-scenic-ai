## 一、★ 先说一个架构变化：数据源变了

旧项目的数据分析，靠的是 Django 自己的 `ChatMessage` 表（那里有
`latency_ms` / `rag_hit` / `retrieval_mode` / `sentiment` / `hot_spot`）。

**但现在对话跑在 Fay 里，Django 不再经手，那些字段就没有了。**

新架构下的数据分布在四处：

| 数据源 | 有什么 | 缺什么 |
|---|---|---|
| **Fay `memory/fay.db` → `T_Msg`** | 46 行对话：`type`(member/fay)、`content`、`createtime`、`username` | ❌ **没有延迟、没有命中率、没有检索路径** |
| **Fay `user_profiles.db` → `T_Member`** | 用户画像 `user_portrait` | —— |
| **Fay `memory/User/memory_stream/`** | 记忆节点、向量 | —— |
| **插件自己的索引** | 条数、语料版本、受保护数 | ❌ **没有被调用过几次、命中了哪些块** |

**结论：想做"RAG 命中率、响应延迟、热点查询"这类看板，必须补埋点。**

## 二、★ 埋点放在插件里（一举两得）

**设计**：每个 MCP 插件把每次调用记成一行 JSONL：

```json
{"ts": "2026-09-25T20:31:02", "tool": "lingshan_query",
 "query": "灵山大佛有多高", "reliable": true, "count": 3,
 "elapsed_ms": 42, "top_kb": ["kb-3f2a...", "kb-8c11..."], "max_distance": 0.2244}
```

**为什么放插件里而不是 Fay 里**：

1. 不用改 Fay 代码
2. 插件才知道"命中了哪几条知识"（Fay 只看到返回文本）

**这一举两得**：

| 用途 | 说明 |
|---|---|
| **管理端分析** | 调用量、命中率、延迟、热点查询 |
| **★ 自进化的输入** | 「哪些问题答不上来」（`reliable=false`）、「哪些知识从没被命中」——**这正好补上之前记的"知识块命中埋点"缺口** |

**图谱插件**（`graph_query`）：

```json

 "ts": "2026-09-25T20:08:19", "plugin": "graph"}
```

两个关键字段：

| 字段 | 为什么重要 |
|---|---|
| **`top_kb`**（命中了哪几条知识） | 管理端做"知识块命中分布"、**自进化做"哪些知识没人问"**的唯一来源——Fay 侧看不到 |
| **`reliable`** | "答不上来的问题"清单 ← 自进化的直接输入 |

### ⚠️ 测量陷阱：`elapsed_ms` 里混进了模型加载时间

实测埋点里 `elapsed_ms` 是 **11000+ ms**，但那**不是检索耗时，是加载 BGE 模型的耗时**。

**原因**：`scripts/mcp_call.py` 每次调用都会**新起一个 MCP server 进程**，
所以每次都重新加载模型。这不是 Fay 的真实场景。

**真实场景下**：MCP server 由 Fay 拉起后**常驻**，模型只加载一次，
之后每次查询应该只有几十毫秒。

**已做的缓解**：在 `build_server()` 里加了**后台预热线程**（进程一起来就加载模型），
并用**加载锁**保护（预热线程和首次查询可能同时触发加载，
`sentence_transformers`/`torch` 的懒加载不是线程安全的——
实测撞出过 `maximum recursion depth exceeded`）。

**待验证**：经 Fay 调用时的真实 `elapsed_ms`（应该远小于 11000）。

### ★ 踩到一个经典前端坑：HTML 不支持自闭合的自定义标签

第一版页面**只渲染出顶栏，下面全空**。DOM 里 `.wrap` 只有一个 `<!---->`。

**根因**：

```html
<el-alert v-if="error" ... />     <!-- 在 .html 的 in-DOM 模板里，这个 "/" 无效 -->
<el-tabs> ... </el-tabs>
```

HTML 解析器**不认自闭合的自定义标签**，`<el-alert .../>` 被当成"开标签"，
于是 `<el-tabs>` 及之后所有内容**都变成了 el-alert 的子元素**；
而 `v-if="error"` 是 false，**整块就渲染成了一个注释**。

**修法**：所有自定义标签必须写完整闭合 —— `<el-alert ...></el-alert>`。

> 这条只影响**写在 .html 里的 in-DOM 模板**。
> 用 SFC（`.vue` 文件 + 构建）不会有这个问题，因为模板由 Vue 编译器处理。
> 之所以能撞上，是因为本项目为了免安装用了单文件 + 本地库的方案。

## 八、知识缺口分析 + 拒答分析 ✅（用户指定的两项）

### 1. 换个视角：从「按知识块」改成「按问题类别」

原来的"130 块里 120 块没被用过"**说明不了什么**——大部分块是刚入库的，还没被问过。

新增 `/api/stats/gaps`：把查询归到 12 个类别（门票票价 / 开放时间 / 路线推荐 /
景点介绍 / 位置指引 / 规模参数 / 文化历史 / 注意事项 / 亲子老人 / 交通停车 /
餐饮住宿 / 服务设施），每类给出：

| 字段 | 含义 |
|---|---|
| `query_count` | 这一类被问了多少次 |
| `hit_rate` | 命中率 |
| `kb_chunks` | 知识库里有多少块在支撑这一类 |
| `gap_level` | **high（严重）/ medium（待补）/ ok（充足）** |
| `advice` | **一句人话建议**，直接告诉管理者该补什么 |

**输出示例**（当前样本）：

```
规模参数   查询2  命中100%  知识块22  充足
景点介绍   查询1  命中100%  知识块40  充足
门票票价   查询1  命中100%  知识块1   充足
```

样本多了之后，像「交通停车」「餐饮住宿」「服务设施」这几个类别（资料包里没有对应知识）
会直接暴露成 **high 缺口**。

### 2. 拒答分析：把「正确拒答」和「真缺口」分开

新增 `/api/stats/refusals`，从 `fay.db` 的问答配对里识别拒答，并分两类：

| 类型 | 例子 | 处理 |
|---|---|---|
| **`knowledge_gap`** | 问"有没有轮椅租借"但知识库没有 | ✅ **要补知识** |
| **`out_of_domain`** | 问"今天天气怎么样"、"帮我写段代码" | ❌ **正确行为，不要补** |

**为什么必须分开**：不区分的话，自进化会去补"灵山天气"这种垃圾知识。
域外判定复用了旧项目的 `OUT_OF_DOMAIN_PATTERNS`。

### ⚠️ 过程中修正的四个误导（都是"看起来对、其实错"）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **把系统报错算成"没命中"** | 一次 `maximum recursion depth exceeded` 让「门票票价」命中率从 100% 掉到 50%，**差点让人以为票价知识不够** | 命中率只统计 `ok=true` 的调用；报错单独列成「系统报错（不是知识缺口）」 |
| 2 | **图谱插件的埋点没有 `reliable` 字段** | 那次 `graph_query` 被当成"没命中"，「景点介绍」类命中率假性 0% | 归一化：向量插件读 `reliable`，图谱插件读 `ok` |
| 3 | **规则搬到 `categories.json` 之后，代码里还留着旧名字** —— `looks_like_refusal()` 从未定义、`stats_gaps()` 里还写着 `CATEGORY_RULES` | 「拒答分析」和「知识缺口分析」两块**一直在返回 500**，前端 `catch (e) { }` 把它吞了，页面显示成"全 0 + 一句空提示"，既看不出没数据，也看不出坏了 | 前者按 `refusal_patterns` 补齐；后者改读 `categories_rules()`；前端改成 `loadOptional()`，取不到的接口在页顶弹黄色提醒 |
| 4 | **「平均响应」把冷启动平均进去了** | 47 个样本里 4 次冷启动（加载嵌入模型，9-11 秒），把平均从 19ms 拉到 825ms，**差 43 倍**。而且它只统计检索、不含大模型，用户实际等 15 秒——读者会以为"响应不到一秒" | 卡片改成「检索耗时 · 中位」，主数用中位（19ms），另标冷启动次数与去冷启动中位；新增「端到端响应 · 中位」卡片（读 `latency-raw.jsonl`）；顶栏加「刷新数据」按钮 |

> 教训：**统计口径比统计本身更重要**。
> 把"故障"和"缺口"混在一起，会让人去补一条本来不缺的知识。
